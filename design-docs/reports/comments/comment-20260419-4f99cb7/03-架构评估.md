# 03 - 架构评估

## 依赖方向

```
cli.py
  ↓
configs/ ──────→ generator/ ──────→ readers/
  ↓                  ↓                ↓
parameters/      population.py    base.py
  ↓              connection.py    csv_reader.py
factory.py       stimulation.py   spreadsheet.py
model.py         io.py            white.py
loader.py            ↓
bio.py          utils/helpers.py
cell_builder.py
custom_types.py
```

**依赖规则：**
- 上层 → 下层（configs → generator → readers → utils）
- parameters 被 generator 和 configs 共同引用
- **无循环依赖**：`parameters/__init__.py` 使用延迟导入打破潜在环路

## 设计模式评审

### ✅ 注册器模式（Configs）

```python
@register_config("IClamp")
def setup(level, ...):
    ...
```

优点：
- 新增配置只需添加文件 + 装饰器，无需修改注册表
- `get_config(name)` 提供统一入口
- 懒加载：仅在首次访问时导入配置模块

不足：
- `_auto_import()` 中仍有硬编码模块列表（16 个），非自动发现

### ✅ 工厂 + 模板方法模式（Parameters）

```python
_LEVEL_TO_CLASS = {
    "A": _IafModel, "B": _IafActivityModel, "BC1": _BC1Model,
    "C": _HHModel, "C0": _HHC0Model, "C1": _HHC1Model,
    "C2": _C2Model, "D": _HHMultiCompModel, "D1": _HHGradedModel,
    "W2D": _W2DModel,
}

def create_model(level: str) -> c302ModelPrototype:
    cls = _LEVEL_TO_CLASS[level]
    return cls()
```

优点：
- 层级查找 O(1)，扩展性好
- 继承层次反映了生物模型的复杂度递进

不足：
- 11 个类挤在单文件中
- 方法级重复严重（详见下文）

### ✅ 抽象基类模式（Readers）

```python
class BaseDataReader:
    def read_data(self): ...
    def read_muscle_data(self): ...
```

优点：
- 清晰的接口契约
- `ConnectionInfo` 数据类消除了松散的元组传递

### ✅ 编排器模式（Generator）

`generate()` 函数作为门面，协调 population、connection、stimulation、io 四个子模块。

优点：
- 职责分离清晰
- 子模块可独立测试

不足：
- `generate()` 参数过多（15+ 个），可考虑封装为配置对象

### ⚠️ 延迟导入模式（Parameters/__init__）

```python
def get_parameter_set(level):
    from c302.parameters.factory import create_model
    return create_model(level)
```

优点：打破潜在循环依赖
不足：隐式依赖，IDE 跳转不友好

## 模块内聚度评估

| 模块 | 内聚度 | 说明 |
|------|--------|------|
| `configs/` | **高** | 每个文件对应一个实验配置，职责单一 |
| `readers/` | **高** | 每个文件对应一种数据源格式 |
| `generator/` | **中高** | 按功能拆分（种群/连接/刺激/输出），但编排器仍较大 |
| `parameters/` | **中** | model.py/bio.py/loader.py 各司其职，但 factory.py 承载过多 |
| `visualization/` | **高** | 每个文件对应一种可视化类型 |
| `simulation/` | **高** | 单一 runner，职责清晰 |
| `utils/` | **中** | helpers.py 为杂项集合 |

## 模块耦合度评估

| 耦合关系 | 耦合度 | 说明 |
|----------|--------|------|
| configs → generator | **低** | 仅调用 `generate()` 入口 |
| configs → parameters | **低** | 通过 `get_parameter_set()` 获取模型 |
| generator → parameters | **中** | 深度使用 `c302ModelPrototype` 接口 |
| generator → readers | **低** | 通过 `_load_data_reader()` 动态加载 |
| factory → model | **高** | 11 个类继承自 `c302ModelPrototype` |
| factory → custom_types | **高** | 直接构造 9 种自定义组件 |

**耦合风险点：** `factory.py` 是整个参数层的"引力中心"——它依赖 model、loader、cell_builder、custom_types 四个模块，同时被 generator 和 configs 间接调用。任何 factory 变更都可能产生连锁影响。

## 总体架构评价

**优点：**
1. 从扁平结构到 7 子包分层，模块边界清晰
2. 依赖方向单一（无循环），包导入安全
3. 注册器/工厂/编排器三种模式恰当运用
4. 新增 CLI 提供了标准化的使用入口

**不足：**
1. `factory.py` 是"新的 God Object"——虽然从原始 10 个文件合并而来，但 1,877 行单文件仍过于庞大
2. 字符串匹配模式（参数查找、细胞分类）偏脆弱
3. `generate()` 函数参数过多，接口复杂
