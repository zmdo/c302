# 附录 - 注释任务执行要求

> 本文档总结阶段二至阶段四的实际执行经验，作为后续阶段（五、六、七）的**可执行操作规范**。
> 每个文件的注释任务必须**严格按照以下步骤顺序**执行。

---

## 一、单文件注释任务的标准流程

每个待注释文件的完整流程分 7 步，**不可跳步**：

```
步骤 1  调研目标文件
   ↓
步骤 2  编写 docstring YAML 规范
   ↓
步骤 3  运行 add_docstring.py
   ↓
步骤 4  添加 SP-CODE-2026-001 文件头
   ↓
步骤 5  添加/翻译行内注释
   ↓
步骤 6  更新索引（gen_index.py 收敛 + check_index.py）
   ↓
步骤 7  等价性验证（verify_comment_only.py）
```

---

## 二、各步骤详细要求

### 步骤 1：调研目标文件

**目的**：在动手之前全面了解目标文件，避免遗漏。

执行内容：
1. 统计文件总行数、函数数量、类数量
2. 统计现有注释数量（`grep -c '^\s*#' <file>`）及语言（英文/中文/混合）
3. 识别哪些函数/方法已有 docstring、哪些没有
4. 识别需要翻译的英文注释行（`grep -n '^\s*#\s*[A-Z]' <file>`）
5. 区分**活跃注释**和**注释掉的代码**（后者保持原样，不翻译）

**输出**：心理清单或会话笔记，明确以下数字：
- N 个函数需要添加 docstring
- M 条英文注释需要翻译
- K 个代码段需要添加段落注释

### 步骤 2：编写 docstring YAML 规范

**工具**：`$SKILL_SCRIPTS/add_docstring.py --spec <yaml>`

> **路径约定**：后续步骤中 `$SKILL_SCRIPTS` 均指代
> `.github/skills/python-annotation-engineering/scripts`

YAML 规范文件必须遵循以下格式：

```yaml
- file: project/c302/目标文件.py
  functions:
    - name: function_name          # 顶层函数
      docstring: |
        函数功能的中文描述。

        :param arg1: 参数说明
        :return: 返回值说明
    - name: ClassName.method_name  # 类方法（用 . 分隔）
      docstring: |
        方法功能的中文描述。
```

**关键规则**：
- 顶层必须是**列表**（以 `- file:` 开头），不能是字典
- docstring 使用 `|` 块标量，保持换行
- 若函数已有 docstring，工具会自动跳过（幂等）
- 建议使用 Python 脚本（`yaml.dump()`）生成 YAML，避免手写时的缩进/引号问题
- 规范文件建议保存到项目中的 `specs/` 或 `scripts/specs/` 目录

**docstring 内容要求**：
- 首行为一句话功能概述
- 空一行后列出参数（`:param name: 说明`）和返回值（`:return: 说明`）
- 使用 reST 格式
- 参考 `design-docs/glossary.md` 中的术语翻译
- 不要翻译参数名、变量名、类名（保持代码原名）

### 步骤 3：运行 add_docstring.py

```bash
python $SKILL_SCRIPTS/add_docstring.py --spec <spec>.yaml
```

**验收标准**：
- 输出应显示 "共添加 N 个 docstring"
- 若有 "已存在 docstring，跳过" 属于正常情况
- 若报错 "规范文件顶层须为列表"，检查 YAML 格式

### 步骤 4：添加 SP-CODE-2026-001 文件头

文件头必须包含以下完整结构（`=====` 分隔线不可省略）：

```python
# =============================================================================
# 功能描述：
#   一句话说明文件用途。
#   可以分多行补充。
#
# 类与方法索引：
#   function_name                        (L行号)  — 函数一句话描述
#   ClassName                            (L行号)  — 类描述
#     method_name                        (L行号)  — 方法描述（缩进两格表示从属）
#
# 更新日志：
#   2026-04-16  操作者  操作描述
#
# 当前维护者：操作者
# =============================================================================
```

**关键规则**：
- 「功能描述」「类与方法索引」「更新日志」「当前维护者」四个块缺一不可
- 索引块由 `gen_index.py --write` 自动生成，**不要手写行号**
- 若文件原本无头部，先手动添加功能描述 + 更新日志 + 维护者三个块，再运行 gen_index.py 补充索引
- 若文件已有索引但缺少其他块，手动补齐缺失块

### 步骤 5：添加/翻译行内注释

本步骤工作量最大，需区分三种操作：

#### 5a. 翻译现有英文注释

- 将 `# English comment` 替换为 `# 中文注释`
- **注释掉的代码行**（如 `# print(x)`, `# old_var = ...`）保持原样，不翻译
- 参考 `design-docs/glossary.md` 统一术语

#### 5b. 添加段落注释（大函数分段）

- 对超过 50 行的函数，在逻辑段之间添加 `# ── 步骤 N：描述 ──` 格式的段落注释
- 段落注释使用全角破折号 `──` 包围，与普通注释区分
- 示例：

```python
    # ── 步骤 1：处理参数覆盖（param_overrides）──
    regex_param_overrides = {"mirrored_elec_conn_params": {}}
    ...

    # ── 步骤 2：创建所有细胞和突触模型组件 ──
    params.create_models()
```

#### 5c. 添加关键行尾注释

- 对含义不直观的赋值/条件行，在行尾添加 `  # 说明`
- 不要对每一行都加注释，只注释**需要领域知识才能理解的行**

**批量操作建议**：
- 对注释量大的文件（>30 条），建议编写 Python 脚本批量替换，避免逐条手动编辑出错
- 脚本使用精确字符串匹配（`str.replace(old, new, 1)`），不要用正则替换代码行
- 辅助脚本保存到 `scripts/` 目录并随代码一起提交

### 步骤 6：更新索引并验证收敛

```bash
# 第一遍：更新行号
python $SKILL_SCRIPTS/gen_index.py <file> --write

# 第二遍：索引本身会改变行号，需再更新一次
python $SKILL_SCRIPTS/gen_index.py <file> --write

# 验证收敛
python $SKILL_SCRIPTS/check_index.py <file>
```

**关键规则**：
- gen_index.py 必须**逐文件**调用，不支持一次处理多文件
- 至少运行 **2 遍**直到 check_index.py 输出 "✅ 所有文件的「类与方法索引」与实际代码一致"
- 若 2 遍后仍不收敛，继续运行直到收敛（极少见）

### 步骤 7：等价性验证

```bash
# 从 git 提取修改前的原始文件
python -c "
import subprocess
data = subprocess.check_output(['git', 'show', 'HEAD:path/to/file.py'])
open('临时文件路径', 'wb').write(data)
"

# 运行验证
python $SKILL_SCRIPTS/verify_comment_only.py <原始文件> <修改后文件>
```

**验收标准**：
- 输出必须为 `[OK]   文件名 — 代码等价，仅注释变更`
- 若输出 `[FAIL]`，说明不小心改动了代码逻辑，必须定位并修复后重新验证

**注意事项**：
- 不要使用 PowerShell 的 `Out-File` 导出 git show 内容，会引入 BOM 导致哈希不匹配
- 使用 Python 的 `subprocess.check_output()` 以二进制方式提取原始文件

## 三、提交规范

### 单阶段提交

每个阶段完成后整体提交一次：

```bash
git add <所有修改文件> <辅助脚本> <YAML规范> <任务清单>
git commit -m "feat: 计划1 — 完成阶段N：层名注释" \
  -m "- 为 X 个函数添加中文 docstring" \
  -m "- 添加 SP-CODE-2026-001 规范文件头" \
  -m "- 翻译 Y 条英文注释为中文" \
  -m "- verify_comment_only.py 验证通过：代码等价，仅注释变更"
```

### 提交前检查清单

- [ ] 所有目标文件都有完整的 SP-CODE-2026-001 文件头
- [ ] 所有函数/方法都有中文 docstring
- [ ] 所有英文活跃注释已翻译为中文
- [ ] check_index.py 输出 ✅
- [ ] verify_comment_only.py 对每个文件输出 `[OK]`
- [ ] 05-任务清单.md 中对应子项已勾选 `[x]`

## 五、已知陷阱与解决方案

| 陷阱 | 症状 | 解决方案 |
|------|------|---------|
| YAML 格式错误 | `规范文件顶层须为列表` | 用 Python `yaml.dump()` 生成 YAML，不要手写 |
| gen_index.py 批量调用 | 多文件参数但只更新 1 个 | 必须逐文件循环调用 |
| gen_index.py 未收敛 | check_index.py 报行号不匹配 | 多跑几遍 `--write` 直到收敛 |
| PowerShell BOM | verify 报首行差异 `\ufeff` | 用 Python `subprocess` 提取 git 文件，不用 `Out-File` |
| 注释掉的代码被翻译 | verify 报 FAIL（代码不等价） | 仅翻译活跃注释，`# var = xxx` 形式的保持原样 |
| 字符串内含 `#` | verify 误报 | verify 使用 `tokenize` 精确识别，不会误判；若遇到需检查是否改动了字符串 |
| 多处重复上下文 | `replace_string_in_file` 报多处匹配 | 增加上下文行数，或使用行号定位脚本替换 |

## 六、术语翻译一致性要求

若项目维护有领域词汇表（如本项目的 `design-docs/glossary.md`），
则所有注释中的领域术语翻译必须与词汇表保持一致。

**建议做法**：在项目根目录或 `design-docs/` 下创建 `glossary.md`，
收录领域内中英对照术语，格式如下：

```markdown
| 英文 | 中文 | 禁止译法 | 说明 |
|------|------|---------|------|
| thread pool | 线程池 | 线程塘 | 并发编程术语 |
```

本项目的完整术语表见 `design-docs/glossary.md`。
